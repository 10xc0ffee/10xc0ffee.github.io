Data preparation

I would like to first summarize the deep learning training process. The first step is data preparation. During data preparation, insufficient data volume can be a significant problem, and you often don’t have a large amount of data readily available. In deep learning architectures, you must have sufficient data for the model to achieve good performance. This is particularly true in some cases, such as when you need video and audio information but cannot obtain enough data. In such situations, there is a technique called data augmentation, which generates synthetic data through manual or machine-generated methods. For example, for image data, you can augment it by flipping, cropping, rotating, or even artificially adding weather effects in computer vision scenarios, such as foggy weather. Through these artificial synthesis methods, you can increase the data volume. When you have sufficient data volume and labels, you need to split the overall data. Common splits are training set, dev set, and test set. Each dataset has a different purpose: the training set is the largest group, used to train the model; the dev set is used during development to quickly validate the trained model’s performance and generally doesn’t need to be particularly large; the test set is used after the training set and dev set achieve ideal training results, serving to verify whether the model can generalize to unseen data.

There is a tricky point here: whether the training set needs to be from the same distribution as the dev/test set. The answer is no. Often, you don’t have enough training data, so you can add data from other sources to the training set. An example is training a security camera to recognize faces. If you don’t have enough security camera data, you can use internet image data for combined training. However, the dev/test set should not include these other sources of data, because the training goal is to ensure the model performs well on security cameras, not to generalize to internet data. The prerequisite is that the external data has the same nature as the target task, meaning it has transferable characteristics. This technique is very similar to the transfer learning mentioned earlier: first train a model using certain data, then retrain the last few layers to adapt to new data. The difference is that in transfer learning, the initial model’s data source may be completely different from the new training model’s data source. For example, you can use a large image model as a base, then perform transfer learning (fine-tuning) with new cat images, hoping the model can specifically recognize cat-related features.

Diagnose Your Model

Now, let’s discuss some techniques and considerations for dev and test sets during the training process. First, your training objective: the first step is to make the model trained on the training set fit the dev set, but this does not necessarily mean the model can fit or generalize to the test set. The differences between the training set and dev set, as well as between the dev set and test set, can be called variance. The former difference usually means the training set is insufficient or the model is overfitting the training set, in which case you need to increase training data or use regularization to reduce overfitting during training. The latter difference means the model is overfitting the dev set, which indicates the dev set is insufficient, and you typically need to increase the dev set.

If during training the training set accuracy is low, but the dev set accuracy is similar to the training set accuracy, this usually means the model has a lot of optimizable bias. This needs to be compared with the Bayes error. Human error is typically used to approximate Bayes error, because humans have high accuracy in most scenarios, so we can consider Bayes error to be close to human error. If human error is already close to dev/training error, we can consider that there is essentially no optimizable bias.

Finally, there are two additional points regarding training, dev, and test sets. First, you may introduce a training-dev set, making the data split: training set, training-dev set, dev set, and test set. This is to distinguish between two training problems:

  1. Training set error is low, but dev set error is high. This may be because the training data and dev data have different distributions. Adding a training-dev set allows you to determine whether the model is training well on the training set by comparing training set error with training-dev set error.
  2. Training-dev set error is similar to training set error, but dev set error is high. This may be because the dev set has insufficient data (requiring data augmentation to increase data volume) or the dev set and training set have different data distributions (requiring adding data similar to the dev set to the training set). Specific situations require manual analysis of error examples.

Transfer Learning and Multitask Learning

The second course also covered some training techniques, such as transfer learning and multitask learning. I just mentioned transfer learning. Now let’s discuss multitask learning. Multitask learning completes multiple tasks in a single training process, with the prerequisite that the tasks have the same attributes. For example, training to recognize multiple objects in an image at once. This is common in computer vision, such as cars, stop signs, pedestrians, etc. The training results output multiple outputs, each corresponding to the probability of a category. Unlike single classification problems, in multitask learning, the probabilities of each category do not need to sum to 1.

Note that for softmax: classification problems use softmax + CrossEntropyLoss, but multitask learning only needs CrossEntropyLoss.

Normalization

First, what is normalization? When you have a labeled dataset, you usually do not want to use those inputs directly in your neural network. Because that data is usually not in good shape or in a good distribution for training, directly feeding that data will lead to bad training results (e.g., loss cannot converge). Usually, in a neural network, we want to have a normal distribution (TOD: Explain why in the appendix). So what we want to do is normalize the input data to follow a normal distribution with a unified mean and standard deviation. What you do is calculate the mean and standard deviation of the data and use those to scale your data. We do this because when you’re applying gradient descent algorithms, you don’t want some dimensions of the data to be too wide or too narrow. If one dimension’s data is all within a narrow range from zero to one, while other dimensions have a much wider data distribution, during gradient descent, one dimension might step too far forward while the other dimensions might not be stepping enough. That’s why you want all dimensions to be normalized, so that your gradient descent algorithm is able to make good decisions on all dimensions at the same time. This will help you speed up your training as well.

With that, I would like to introduce batch normalization. Batch normalization is actually similar to normalization. In normalization, we normalize the input data of the input layer. In batch normalization, what we do is normalize all the inputs at each layer. In your neural network, each layer’s data could have different distributions. This will also cause issues in the gradient descent algorithm. So the idea is to normalize your data at each layer. You will calculate the standard deviation and mean at each layer after you have updated the W and b vectors at each layer. And you apply normalization to each layer’s output using the standard deviation and mean value. With that, we actually ensure all layers will generate output with a relatively similar distribution. Regularization

Okay, now let’s talk about regularization. Regularization is a technique to ensure we don’t overfit the training data. A lot of times, you achieve good accuracy on your training data, but when it comes to dev data and test data, we are not able to achieve good accuracy. There are two common regularization algorithms. The first is L2-regularization. The basic idea is that when your model is overfitting your data, this is usually because some of the weights are too large. Optimization

Then let’s talk about optimization. Optimization is one important topic in deep neural networks. You want to be able to get the minimum loss as fast as possible.

The first thing I want to talk about is learning rate decay. The idea is that during your neural network gradient descent at a later stage, when the model is reaching the optimal point in the training data, you don’t want to keep the learning rate too large compared to the initial learning rate; otherwise, you will very easily oscillate around the optimal point. So you won’t be able to have a stable and smaller loss at the end of the training process. So what you do is you can reduce your learning rate gradually during the training process by using different kinds of formulas. For example, you can use a certain learning rate for the first 100 epochs, and then reduce the learning rate in the next 100 epochs, and so on and so forth.

The second mechanism you can use is called momentum. The basic idea is that in each dimension, when you are applying gradient descent, if at that dimension the gradients are oscillating back and forth, you don’t want that to happen. So basically, by applying a weighted average at each gradient descent step, combining all of the historical gradients, you are able to speed up or slow down the updates on every dimension. You want to reduce the zigzag scenarios, where you step too much forward, then backward, then forward, then backward. That scenario will be reduced if you apply this weighted average mechanism for each gradient. Notice that when you are calculating the weighted average, the coefficient beta is very important. So usually we’ll set beta to 0.9. Basically, that means you are looking at the past 10 calculated gradients for this average (1/(1-0.9) = 10, TODO: Describe effective sample in the Appendix). So a lot of people will also divide by one minus beta to the power of t. This is to ensure the calculated average doesn’t decrease in the initial phases.

Saddle Point

And I want to also talk about a concept called saddle points. This is a point during gradient descent where you are not able to find the minimum point, and you are stuck. The optimization should be able to get rid of this saddle point as fast as possible. At a saddle point, you are moving very slowly, as many dimensions at this saddle point are not able to generate large enough gradients. So in the gradient descent algorithm, you are not moving fast, and you are not moving out of this area.

Hyperparameter tuning

What is hyperparameter tuning? As you all know that in deep learning, there will be a lot of different hyperparameters, including learning rate, how many unit layers in your deep neural network, and a lot more described in the following sections of optimization, normalization, and regularization. So you need a way that helps you better find out what the hyperparameters are and how to choose them, to make your model best fit your training set and dev set, and be able to generalize to your test set.

Okay. Finally, let’s talk about when you are tuning those hyperparameters involved in normalization, batch normalization, optimization, and regularization. How should you tune them? So the first very important thing is the learning rate. This is the first thing you have to care about. And then you have to care about the layers in your neural network: how many hidden layers, how many neurons in each layer, and such things. Another thing you want to care about is optimization. Basically, what are the coefficients or hyperparameters you need in your optimization algorithms? This will directly impact the speed of your learning. And then the third thing is regularization and normalization factors, hyperparameters. Finally, let’s talk about the training process. Do you have enough computing power, so that you can try those hyperparameter tuning parameters in parallel? That will be fastest. But if you don’t have enough computing resources, you should babysit your training in person. Basically, tune these parameters dynamically. What you do is you will train for several hours and observe how much the loss reduces, and you observe. If it’s stuck somewhere, you need to tune your hyperparameters dynamically to see if it gets better. And if you don’t have enough computing power, what you do is different. There is a very subtle thing about how you choose your hyperparameters and how you randomly choose them. Usually, you use a log scale to choose them for many of them, because, for example, for a learning rate: if your learning rate is from 0.1 to 0.2, 0.9 and 0.8 are pretty much the same for your training process. But 0.1 and 0.01 have a very big difference. So you should use a log scale to randomly sample your learning rate and try them. And for a combination of hyperparameters, you will usually want to do two things. First, you will try to sample certain areas. Then you divide the search space into four areas for two hyperparameters. And in the four areas, you will observe your training results. And if one of the areas is good, you then jump into that area for further searching. This will be better than keeping the same hyperparameter one and continuously searching hyperparameter two. Because a lot of times, if you fix hyperparameter one, it doesn’t give good results. You’re wasting your time sticking to this hyperparameter value. So you want to do random search first and then jump into some area that gives you good results.
